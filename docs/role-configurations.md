### Shared CLI conversation pilot

Use one private MOBAdev issue as a shared conversation for the first real cross-tool coordination case, subject to authorization for its participants and content. This is a candidate for peer discussion. The COO's existing coordination record continues to own assignments, decisions, and execution state. Native messaging can still deliver a notification when a verified recipient route supports it.

- **Preflight:** Verify that the repository is private and each participating environment can access it with its approved identity. The local GitHub CLI could read the private repository on 2026-11-05, and Issues were enabled. Access from the COO's Claude runtime, the hosted Executive Assistant, and the intended Antigravity environment is open. Avoid granting broader access just to run the pilot.
- **Conversation:** Use a single issue for one topic. In each comment include sender role, recipients or team, the conversation or task reference, and a question, answer, or acknowledgement. Any participant with access can read and reply in the same thread. Record the authenticated GitHub actor separately from the stated agent role. A shared account cannot independently authenticate individual agent roles.
- **Delivery:** Read and post with the GitHub Issues API or `gh`. Verify writes by reading back the comment ID. Separate publication, recipient acknowledgement, and a substantive reply. If the write result is uncertain, read back before retrying. Only add background delivery after the pilot proves that the receiving runtime has a supported way to pick up an event.
- **Data and authority:** Share only team coordination material suitable for the private repository. Keep secrets, private histories, machine-local IDs, and access tokens out of comments. Treat the comments as messages. Changes to source, permissions, execution, or deployment still require their existing authorization.
- **Acceptance:** Use one real bounded coordination question. Each participant confirms from its own environment that it can read the issue and that its reply is visible to the intended recipients. Record the approved identity, supported access path, comment IDs, and observed acknowledgements and replies. A manual read/reply proves pull-based delivery. An automatic wake is a separate capability.
